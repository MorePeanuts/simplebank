# 08. 用 mock 测试 HTTP API

[03. CRUD 单元测试](./03_unit_test_for_crud.md) 给 `db/sqlc` 包写测试时，走的是"起一个真实的 Postgres 容器，直接打数据库"的路线。原因很直接：CRUD 这层就是数据库的薄包装，**测试不打数据库就没测出任何东西**。

到了 [06. RESTful HTTP API](./06_restful_http_api.md) 这层 handler，情况反过来了。handler 关心的是：

- 请求参数有没有正确从 URI / body / query 里解析出来；
- 校验失败时是不是返回 400；
- store 返回 `sql.ErrNoRows` 时是不是返回 404、其他错误是不是返回 500；
- 成功时响应体的 JSON 结构是不是预期的样子。

这些事情**和真实数据库长什么样没有关系**。如果还是起一个真 Postgres 来跑这些测试，会带来三个不必要的代价：

1. **慢**：每次跑测试都要走一次 TCP + SQL 解析 + 落盘往返；
2. **状态共享**：多个 case 之间需要清理或者用唯一字段区分，写起来繁琐；
3. **无法构造异常路径**：想测 "DB 连接断了 handler 该返回 500" —— 你没办法在测试里真的把 Postgres 杀掉再起来。

所以这一节换一种打法：把 `Store` 这一层用 mock 替掉，handler 测试只关心"给定 mock 的返回，handler 的输出对不对"。

## 安装 mockgen

mock 框架用的是 [uber-go/mock](https://github.com/uber-go/mock)（这是 google `golang/mock` 项目归档后的官方延续，API 完全兼容）。它由两部分组成：

- 运行时库 `go.uber.org/mock/gomock`：测试代码里用来设期望、断言调用次数、注入返回值；
- 代码生成器 `mockgen`：扫描接口定义，自动生成实现这些接口的 mock 类型。

```bash
go install go.uber.org/mock/mockgen@latest
go get go.uber.org/mock/gomock
```

## 把 `Store` 改造成接口

mockgen 生成 mock 的前提是**有一个 Go interface 可以被实现**。当前的 `db.Store` 是个具体的 struct：

```go
// db/sqlc/store.go（旧）
type Store struct {
    *Queries
    db *sql.DB
}

func NewStore(db *sql.DB) *Store {
    return &Store{db: db, Queries: New(db)}
}

func (store *Store) execTx(...) error { ... }
func (store *Store) TransferTx(...) (TransferTxResult, error) { ... }
```

handler 直接持有 `*db.Store`，没有抽象层可以替换。改造分两步。

### 第一步：让 sqlc 生成 `Querier` 接口

sqlc 默认只生成 `Queries` 这一个具体类型，所有的 CRUD 方法都挂在它上面。打开 `emit_interface` 后，sqlc 会额外吐出一个把所有方法都收齐的 `Querier` 接口：

```yaml
# sqlc.yaml
sql:
  - engine: "postgresql"
    queries: "./db/query/"
    schema: "./db/migration/"
    gen:
      go:
        package: "db"
        out: "./db/sqlc"
        sql_package: "database/sql"
        sql_driver: "github.com/lib/pq"
        emit_json_tags: true
        emit_empty_slices: true
        emit_interface: true     # 新增
```

重新 `make sqlc`，多出一个 `db/sqlc/querier.go`：

```go
// Code generated by sqlc. DO NOT EDIT.
package db

type Querier interface {
    AddAccountBalance(ctx context.Context, arg AddAccountBalanceParams) (Account, error)
    CreateAccount(ctx context.Context, arg CreateAccountParams) (Account, error)
    CreateEntry(ctx context.Context, arg CreateEntryParams) (Entry, error)
    // ... 其它方法
    ListAccounts(ctx context.Context, arg ListAccountsParams) ([]Account, error)
    UpdateAccount(ctx context.Context, arg UpdateAccountParams) (Account, error)
}

var _ Querier = (*Queries)(nil)
```

### 第二步：把 `Store` 改成接口，原本的 struct 改名 `SQLStore`

```go
// db/sqlc/store.go
type Store interface {
    TransferTx(ctx context.Context, arg TransferTxParams) (TransferTxResult, error)
    Querier
}

// SQLStore provides all functions to execute db queries and transactions
type SQLStore struct {
    *Queries
    db *sql.DB
}

// NewStore creates a new Store
func NewStore(db *sql.DB) Store {
    return &SQLStore{
        db:      db,
        Queries: New(db),
    }
}

func (store *SQLStore) execTx(ctx context.Context, fn func(*Queries) error) error { ... }

func (store *SQLStore) TransferTx(ctx context.Context, arg TransferTxParams) (TransferTxResult, error) { ... }
```

- **`Store` 接口嵌入了 `Querier`**：这样 `Store` 自动获得了 sqlc 那 13 个 CRUD 方法，不需要在接口定义里再列一遍；只需要单独声明 `TransferTx` 这一个事务方法。后续每加一条 SQL 查询，sqlc 重新生成 `Querier` 时 `Store` 就自动跟着扩展了。如果有新的事务，则需要在 `Store` 中声明。
- **`execTx` 仍然挂在 `*SQLStore` 上**：这是只在 `SQLStore` 内部用的辅助方法，属于实现细节，不进接口。

### 第三步：让 handler 依赖接口而不是具体类型

`api/server.go` 里把 `*db.Store` 改成 `db.Store`：

```go
type Server struct {
    store  db.Store        // 旧：*db.Store
    router *gin.Engine
}

func NewServer(store db.Store) *Server {   // 旧：store *db.Store
    server := &Server{store: store}
    // ...
}
```

到这一步，handler 已经不再认识"真实的 SQL 实现"了，只认接口。下一步就能拿一个 mock 实现塞进去。

## 用 mockgen 生成 `MockStore`

`mockgen` 的命令格式是：

```
mockgen -package <生成包名> -destination <输出文件> <要 mock 的接口所在 go 包> <接口名>
```

把它放到 `Makefile` 里：

```makefile
mock:
	mockgen -package mockdb -destination db/mock/store.go github.com/MorePeanuts/simplebank/db/sqlc Store

.PHONY: postgres createdb dropdb migrateup migratedown sqlc test server mock
```

跑一次 `make mock`，会生成 `db/mock/store.go`：

```go
// Code generated by MockGen. DO NOT EDIT.
package mockdb

type MockStore struct {
    ctrl     *gomock.Controller
    recorder *MockStoreMockRecorder
    isgomock struct{}
}

func NewMockStore(ctrl *gomock.Controller) *MockStore { ... }
func (m *MockStore) EXPECT() *MockStoreMockRecorder { ... }

// 每个接口方法生成两个：
// 1) 真正实现接口的 method，把调用转交给 ctrl
func (m *MockStore) GetAccount(ctx context.Context, id int64) (db.Account, error) {
    m.ctrl.T.Helper()
    ret := m.ctrl.Call(m, "GetAccount", ctx, id)
    ret0, _ := ret[0].(db.Account)
    ret1, _ := ret[1].(error)
    return ret0, ret1
}
// 2) 给 EXPECT() 用的 recorder 方法，用来设置预期
func (mr *MockStoreMockRecorder) GetAccount(ctx, id any) *gomock.Call { ... }
```

每个接口方法都会生成一对：业务调用走第一个，测试里 `store.EXPECT().GetAccount(...)` 走第二个。

### 工作原理：录制 / 回放

gomock 走的是经典的 **录制 → 回放**（record-then-replay）模型，整个流程围绕一个中央调度器 `gomock.Controller` 展开。先把生成代码里几个角色摆清楚：

- **`MockStore`**：实现了 `Store` 接口的"假货"。每个方法体里**没有任何真实业务**，只是把"方法名 + 入参"打包丢给 `ctrl.Call(...)`，再把 controller 返回的值当作自己的返回值。
- **`MockStoreMockRecorder`**：和 `MockStore` 形状镜像，但每个同名方法返回的是 `*gomock.Call` —— 一个可以链式调用 `.Times(n).Return(...)` 的"期望对象"。它本身不执行任何业务，只负责"把一条期望注册进 controller"。
- **`gomock.Controller`**：核心调度器，内部维护一张"已注册期望"的清单，负责匹配、记账、校验。
- **`EXPECT()`**：`MockStore` 上的一个方法，仅有的作用是返回它内部那个 recorder，让 `store.EXPECT().GetAccount(...)` 这种链式写法成立。

为什么要把"业务方法"和"recorder 方法"做成两套同名的？因为如果共用一个，就分不清"调用方是想真的调一次 GetAccount"还是"调用方是想注册一条 GetAccount 的期望"。分成 `store.GetAccount(...)` 和 `store.EXPECT().GetAccount(...)` 这两条路径，语义就清楚了。

**录制阶段**：测试里的 `buildStubs` 是在告诉 controller "等会儿 handler 应该怎么调我"。

```go
store.EXPECT().
    GetAccount(gomock.Any(), gomock.Eq(account.ID)).
    Times(1).
    Return(account, nil)
```

逐段拆开：

1. `store.EXPECT()` 拿到 recorder。
2. `.GetAccount(gomock.Any(), gomock.Eq(account.ID))` 调用的是 `MockStoreMockRecorder.GetAccount`。它的实现大致是 `return ctrl.RecordCallWithMethodType(...)`，作用是**往 controller 里塞一条期望**："如果有人调用名为 `GetAccount`、第一个入参随便、第二个入参等于 `account.ID` 的方法，请用这条期望来匹配。" 返回 `*gomock.Call` 用来继续配置。
3. `.Times(1)` 把这条期望的匹配次数上限设成 1。
4. `.Return(account, nil)` 把这次匹配命中后要返回的值挂到这条期望上。

注意，整个录制过程**没有真的调用 `MockStore.GetAccount`**，handler 也还没跑。controller 这时候只是在攒一张"剧本"。

**回放阶段**：`server.router.ServeHTTP(...)` 触发 handler，handler 调 `server.store.GetAccount(ctx, req.ID)`。这次走的是 `MockStore.GetAccount`，方法体里：

```go
ret := m.ctrl.Call(m, "GetAccount", ctx, id)
```

`Call` 会拿"方法名 + 实际入参"去剧本里找一条还没被吃光的、参数能匹配上的期望：

- **找到了**：把那条期望的 `Return(...)` 值返回给 handler，并把这条期望的剩余次数减 1。
- **找不到**（没注册过、或注册过但参数不对、或次数已经用完）：直接 `t.Fatalf` 报 "Unexpected call to ..."。

`Times(0)` 那种 case 就是显式声明"这条根本不该被调到"，gomock 会在 case 结束时一并校验。

**收尾**：`defer ctrl.Finish()` 在 case 结束时遍历剧本，检查每条期望"实际命中次数"和"声明的次数"是否一致 —— 录了 `Times(1)` 但 handler 一次没调、或者录了 `Times(0)` 但 handler 调了一次，都会在这里被抓出来。

所以这套机制本质上是用 controller 把 `mock 方法实际入参 ↔ 测试声明的期望参数` 这件事**变成可断言的**。代码生成器 mockgen 的全部价值就在于：批量产出"把每个方法调用塞进 controller"的样板代码 —— `Store` 接口里加一个新方法，`make mock` 重新跑一次就够了，不用手写。

## 给 `GET /accounts/:id` 写测试

handler 测试的入口放在 `api/account_test.go`，先聚焦最简单的 `getAccount`，跑通整个 mock 测试的骨架。

### 测试入口 `api/main_test.go`

```go
package api

import (
    "os"
    "testing"

    "github.com/gin-gonic/gin"
)

func TestMain(m *testing.M) {
    gin.SetMode(gin.TestMode)
    os.Exit(m.Run())
}
```

`gin.SetMode(gin.TestMode)` 的作用是关掉 gin 默认的调试日志（路由表打印、每条请求的访问日志）。测试跑起来时终端只剩有意义的输出，不会被 gin 的样板日志淹没。

### 表驱动 + 四种 case

```go
func TestGetAccountAPI(t *testing.T) {
    account := randomAccount()

    testCases := []struct {
        name          string
        accountID     int64
        buildStubs    func(store *mockdb.MockStore)
        checkResponse func(t *testing.T, recorder *httptest.ResponseRecorder)
    }{
        {
            name:      "OK",
            accountID: account.ID,
            buildStubs: func(store *mockdb.MockStore) {
                store.EXPECT().
                    GetAccount(gomock.Any(), gomock.Eq(account.ID)).
                    Times(1).
                    Return(account, nil)
            },
            checkResponse: func(t *testing.T, recorder *httptest.ResponseRecorder) {
                require.Equal(t, http.StatusOK, recorder.Code)
                requireBodyMatchAccount(t, recorder.Body, account)
            },
        },
        {
            name:      "NotFound",
            accountID: account.ID,
            buildStubs: func(store *mockdb.MockStore) {
                store.EXPECT().
                    GetAccount(gomock.Any(), gomock.Eq(account.ID)).
                    Times(1).
                    Return(db.Account{}, sql.ErrNoRows)
            },
            checkResponse: func(t *testing.T, recorder *httptest.ResponseRecorder) {
                require.Equal(t, http.StatusNotFound, recorder.Code)
            },
        },
        {
            name:      "InternalError",
            accountID: account.ID,
            buildStubs: func(store *mockdb.MockStore) {
                store.EXPECT().
                    GetAccount(gomock.Any(), gomock.Eq(account.ID)).
                    Times(1).
                    Return(db.Account{}, sql.ErrConnDone)
            },
            checkResponse: func(t *testing.T, recorder *httptest.ResponseRecorder) {
                require.Equal(t, http.StatusInternalServerError, recorder.Code)
            },
        },
        {
            name:      "InvalidID",
            accountID: 0,
            buildStubs: func(store *mockdb.MockStore) {
                store.EXPECT().
                    GetAccount(gomock.Any(), gomock.Any()).
                    Times(0)
            },
            checkResponse: func(t *testing.T, recorder *httptest.ResponseRecorder) {
                require.Equal(t, http.StatusBadRequest, recorder.Code)
            },
        },
    }

    for _, tc := range testCases {
        t.Run(tc.name, func(t *testing.T) {
            ctrl := gomock.NewController(t)
            defer ctrl.Finish()

            store := mockdb.NewMockStore(ctrl)
            tc.buildStubs(store)

            server := NewServer(store)
            recorder := httptest.NewRecorder()

            url := fmt.Sprintf("/accounts/%d", tc.accountID)
            request, err := http.NewRequest(http.MethodGet, url, nil)
            require.NoError(t, err)

            server.router.ServeHTTP(recorder, request)
            tc.checkResponse(t, recorder)
        })
    }
}
```

- **`server.router.ServeHTTP(recorder, request)`**：这是 `net/http/httptest` 的核心套路 —— 不实际起一个 TCP 监听端口，而是直接把 `(ResponseWriter, *Request)` 喂给路由器。`httptest.NewRecorder()` 实现了 `http.ResponseWriter`，把 handler 写出去的状态码、header、body 都缓存在内存里，便于断言。整个测试不开端口、不 fork 进程，速度只比一次函数调用慢一点点。

### 工具函数

```go
func randomAccount() db.Account {
    return db.Account{
        ID:       util.RandomInt(1, 1000),
        Owner:    util.RandomOwner(),
        Balance:  util.RandomMoney(),
        Currency: util.RandomCurrency(),
    }
}

func requireBodyMatchAccount(t *testing.T, body *bytes.Buffer, account db.Account) {
    data, err := io.ReadAll(body)
    require.NoError(t, err)

    var getAccount db.Account
    err = json.Unmarshal(data, &getAccount)
    require.NoError(t, err)
    require.Equal(t, account, getAccount)
}
```

`randomAccount` 复用了之前在 [03. CRUD 单元测试](./03_unit_test_for_crud.md) 里写好的 `util.Random*` 系列。`requireBodyMatchAccount` 把"body → []byte → JSON → struct → 等值断言"这条链子封起来，避免在每个 case 里重写一次。

```go
func TestCreateAccountAPI(t *testing.T) {

    testCases := []struct {

                    })).
                    Times(1).

            // ...
        },
        {name: "InvalidCurrency", accountCurrency: "RMB", /* Times(0), 期望 400 */},
        {name: "MissingOwner", accountOwner: "", /* Times(0), 期望 400 */},

                require.Equal(t, http.StatusInternalServerError, recorder.Code)

            },
        },
    }

    for _, tc := range testCases {
        t.Run(tc.name, func(t *testing.T) {
            // ...
            requestBody := struct {

            }{tc.accountOwner, tc.accountCurrency}
            jsonData, err := json.Marshal(requestBody)
            require.NoError(t, err)

            // ...
        })

```

测试里 `gomock.Eq` 对入参的等值断言把"`Balance` 必须是 0"这条 [06 节](./06_restful_http_api.md#创建账户-post-accounts) 提到的安全边界从代码里抬到了测试里。

### 测试抓出来的 bug：`InternalError` case 没过

四个 case 跑下来，`InternalError` 这个 case 挂了：

```
=== RUN   TestCreateAccountAPI/InternalError
[GIN] 2026/06/14 - 22:28:28 | 500 | 191.459µs |                 | POST     "/accounts"
    account_test.go:452:
        Error Trace:	api/account_test.go:452
                        api/account_test.go:112
                        api/account_test.go:139
        Error:      	Received unexpected error:
                        invalid character '{' after top-level value
        Test:       	TestCreateAccountAPI/InternalError
--- FAIL: TestCreateAccountAPI/InternalError (0.00s)
```

注意两个细节：

1. gin 那行访问日志显示 `| 500 |` —— 状态码其实是对的；
2. 真正挂掉的是 `requireBodyMatchError` 里那次 `json.Unmarshal`，错误信息是 `invalid character '{' after top-level value`。

"top-level value 之后又出现了 `{`"，意思是 JSON 解析器吃完第一个完整的对象后，发现 buffer 里还有内容。换句话说 —— body 里是**两段 JSON 首尾相连**。翻回 [06 节](./06_restful_http_api.md#创建账户-post-accounts) 的 `createAccount` 实现：

```go
account, err := server.store.CreateAccount(ctx, arg)
if err != nil {
    ctx.JSON(http.StatusInternalServerError, errorResponse(err))
    // 这里漏了 return!
}

ctx.JSON(http.StatusOK, account)
```

错误分支没有 `return`，于是控制流继续往下又调了一次 `ctx.JSON(http.StatusOK, account)`。状态码倒是没受影响：gin 在第一次 `ctx.JSON` 时已经把 response header 提交出去了，第二次 `ctx.JSON` 改不动 header。但 body 是直接往 `ResponseWriter` 里 `Write` 的，第二次调用就把 `{"id":0,"owner":"","balance":0,"currency":"","created_at":"..."}` 追加在了第一段 `{"error":"sql: connection is already closed"}` 后面，最终 body 长这样：

```
{"error":"sql: connection is already closed"}{"id":0,"owner":"","balance":0,"currency":"","created_at":"0001-01-01T00:00:00Z"}
```

两段 JSON 拼一起，`json.Unmarshal` 解析完第一个对象后撞上第二个 `{`，报 "top-level value 之后还有内容"。补上 `return` 后再跑：

```go
account, err := server.store.CreateAccount(ctx, arg)
if err != nil {
    ctx.JSON(http.StatusInternalServerError, errorResponse(err))
    return                          // 修复
}

ctx.JSON(http.StatusOK, account)
```

### `GET /accounts`

```go
func TestListAccountsAPI(t *testing.T) {
    accounts := make([]db.Account, 0)
    for range 10 {
        accounts = append(accounts, randomAccount())
    }
    initParams := func(pageID, pageSize int32) db.ListAccountsParams {
        return db.ListAccountsParams{
            Limit:  pageSize,
            Offset: (pageID - 1) * pageSize,
        }
    }

    testCases := []struct {
        name          string
        pageID        int32
        pageSize      int32
        buildStubs    func(store *mockdb.MockStore)
        checkResponse func(t *testing.T, recorder *httptest.ResponseRecorder)
    }{
        {name: "OK", pageID: 1, pageSize: 5, /* 期望 ListAccounts(initParams(1, 5)),返回前 5 条 */},
        {name: "InvalidID", pageID: 0, pageSize: 5, /* Times(0), 期望 400 */},
        {name: "InvalidPageSize", pageID: 1, pageSize: 20, /* Times(0), 期望 400 */},
        {name: "InternalError", /* 期望 500 */},
    }
    // ...
}
```

`initParams` 把 handler 内部那次 `offset = (pageID - 1) * pageSize` 的换算直接复用到测试里 —— 不然测试每个 case 都要手算一次 offset，又啰嗦又容易出错。`OK` case 的 `gomock.Eq(initParams(1, 5))` 同时断言了"分页换算公式必须正确"。

handler 这一层因为没有外部不可控因素，做到 100% 覆盖是合理的目标。当然"100% 覆盖"不等于"测全了" —— 它只代表每行代码至少被一个 case 执行过，并不保证每条业务路径都有断言。但反过来说，**handler 这层如果做不到 100% 覆盖，要么是有死代码，要么是有路径没人想清楚**，两种情况都值得回头看一下。

## 小结

| 改动 | 解决的问题 |
| ---- | ---- |
| `sqlc.yaml` 加 `emit_interface: true` | 让 sqlc 生成 `Querier` 接口，作为 mock 的基础 |
